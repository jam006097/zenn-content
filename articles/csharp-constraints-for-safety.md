## はじめに：なぜ「自由なコード」は危険なのか

「このメソッド、引数に何を入れてもコンパイルは通るけど、本当に大丈夫かな？」
「予期せぬ場所で値が書き換えられていて、原因を特定するのに半日溶かした...」

開発者なら誰でも、こんな経験があるはずです。僕はしょっちゅうです。😭

直感的に「自由度が高いほうが作りやすい」と考えがちですが、ソフトウェア開発において、その自由はしばしば**「間違える原因」**として牙を向きます。しかも、保守フェーズの忘れたころに、、、

『Secure by Design（セキュア・バイ・デザイン）』や『Good Code, Bad Code』では、一貫して**「間違った使い方ができないように設計する」**ことの重要性が説かれています。めちゃくちゃいい本で目から鱗落ちまくりです😍

残酷な事実ですが、**他の開発者（あるいは数ヶ月後の自分）は、あなたが書いたコメントやドキュメントを丁寧には読みません。** 「この引数にマイナスは入れないでください」とコメントに書いても、誰かが必ずマイナスを入れます。

バグを減らす唯一の確実な方法は、ドキュメントに頼るのではなく、**「間違ったコードを書くと、そもそもコンパイルが通らない」という物理的な制約をコードに組み込むこと**です。今回はC#を使って、その具体的な手法を深掘りしていきましょう😊

## 1. プリミティブ型への執着を捨てる

多くのコードで見かけるのが、`int` や `string` といった基本型（プリミティブ型）をそのまま使い回す設計です。これを「プリミティブ型への執着」と呼びます。

### 良くない例：ただの `int`
```csharp
public void RegisterUser(string name, int age) 
{
    // 何でも入ってしまう： -1, 999, int.MaxValue...
    if (age < 0 || age > 150) throw new ArgumentException("無効な年齢です");
}
```

この設計の問題は、`RegisterUser` を呼び出す**すべての場所**で、「この値は正しいかな？」と気を使わなければならない点です。また、`int` 型は何の意図も伝えません。

### 良い例：専用の型（ドメインプリミティブ）を作る

ここでC#の **`record`（レコード）** を活用しましょう。`record` は C# 9.0 から導入された機能で、データの保持に特化した「クラスのようなもの」です。

#### record のここがすごい
- **簡潔さ**: クラスよりも短い記述でデータを定義できます。
- **値による比較**: 普通のクラスは「同じ場所にあるか」で比較されますが、recordは「中身が同じか」で比較されます。
- **不変性（Immutable）**: デフォルトで「一度作ったら変えられない」という性質を持ちます。

```csharp
public record Age
{
    public int Value { get; }

    // コンストラクタで「正しい状態」しか作らせない制約を課す
    public Age(int value)
    {
        if (value < 0 || value > 150) 
            throw new ArgumentException("年齢は0から150の間でなければなりません");
        Value = value;
    }
}
```

### なぜ専用の型を作るのか？
1. **不正な値を物理的に排除**: `Age` 型のオブジェクトが存在している時点で、それは「正しい範囲内の年齢」であることが保証されます。`null` や `-1` が入り込む余地はありません。
2. **コードが「意図」を語る**: `Method(int value)` よりも `Method(Age age)` のほうが、何を渡すべきかが一目でわかります。
3. **ドキュメント不要**: 型そのものが「制約（ルール）」を表しているため、コメントを読まなくても使い方がわかります。

## 2. 「後から変えられない」という安心（不変性と init）

変数の値がどこでも書き換えられる状態は、バグの温床です。特にマルチスレッド環境や複雑なビジネスロジックでは、「いつの間にか値が変わっている」現象がデバッグを地獄に変えます。

ここで役立つのが **`init`（イニット）専用プロパティ** です。

### init プロパティとは？
通常、プロパティを外部から設定できるようにするには `set` を使いますが、これだと「いつでも」書き換えられてしまいます。
対して `init` は、**「オブジェクトを作るときだけ設定可能で、その後は読み取り専用になる」**という制約を課します。

```csharp
public record User
{
    public string Id { get; init; }   // 作成時のみ設定可能
    public string Name { get; init; } // 二度と変更できない
    public int Score { get; private set; } // 変更はクラス内部のメソッドからのみ

    public void AddScore(int point) => Score += point;
}

// 使うとき
var user = new User { Id = "U001", Name = "Alice" };
// user.Name = "Bob"; // ← コンパイルエラー！「変えられない」だから安全。👍
```

「変えられない」ことは不便に思えるかもしれませんが、それは**「その値が一生変わらないことをコンパイラが保証してくれる」**という強大な安心感に繋がります。

## 3. 「ありえない状態」を型で消し去る

例えば、注文の状態（未発送、発送済み、キャンセル）を管理する場合、複数の `bool` フラグを使うと「発送済みかつキャンセル」という矛盾した状態が作れてしまいます。

### 良い例：列挙型（Enum）と switch 式の組み合わせ

C#の **`switch` 式**（C# 8.0〜）を使うと、全ての状態を考慮しつつ、安全にロジックを記述できます。

```csharp
public enum OrderStatus { Pending, Shipped, Cancelled }

public record Order(string Id, OrderStatus Status);

public string GetStatusMessage(Order order) => order.Status switch
{
    OrderStatus.Pending   => "準備中です。",
    OrderStatus.Shipped   => "発送済みです。",
    OrderStatus.Cancelled => "この注文はキャンセルされました。",
    _ => throw new InvalidOperationException("未知のステータスです")
};
```

さらに、もし将来 `OrderStatus` に新しい状態（例えば `Returned`：返品）が追加された場合、コンパイラが「`switch` 式で `Returned` のケースが足りませんよ」と警告（または設定によりエラー）を出してくれます。

「ドキュメントに『新しいステータスを追加したらここも直してね』と書く」のではなく、**「直さないとビルドが通らない状況を作る」**。これこそがプロの設計です。

## 4. null を「存在しないもの」として扱う

C# 8.0 で導入された **「Null許容参照型（Nullable Reference Types）」** も、強力な制約の一つです。
プロジェクト全体でこの機能を有効にすると、普通に `string name` と書いただけで「これは null になってはいけない変数だ」という制約になります。null を許容したい場合は `string? name` と書く必要があります。

```csharp
public void Process(string name) // name に null を渡すと警告が出る
{
    Console.WriteLine(name.Length); // 安心感を持ってアクセスできる
}
```

「nullチェックを忘れないように気をつける」という人間の注意力に頼るのではなく、**「nullの可能性があるならコンパイルを通さない」**という機械的なチェックに任せることで、ランタイムエラーの大部分を未然に防げます。

## まとめ：制約は開発者への「マナー」である

私たちが目指すべきは、「何でもできる魔法の杖」のようなコードではありません。
**「正しいレールの上しか走れない、安全装置付きの列車」**のようなコードです。

1. **プリミティブ型をラップする**: `int` ではなく `Age` 型を作ることで、不正な値と null を排除する。
2. **不変性（record / init）をデフォルトにする**: 「変わらない」ことは、予測可能性という最大の武器になる。
3. **型で意図を伝える**: 名前やコメントではなく、型そのものを「仕様書」にする。

他の開発者はドキュメントを読みません。しかし、**コンパイルエラーは無視できません。**

「不自由」を設計に組み込むことは、一見すると制限が多くて窮屈に感じるかもしれません。しかし、その制限こそが、将来の自分やチームメイトをバグの恐怖から助け出してくれます。

そして、本質的なロジックの実装に集中させてくれることにつながります。
制約は「マナー」なのです。😺

今日から、あなたのコードに少しだけ「制約」を加えてみましょう。
３か月後の自分は大喜びすることになるかも👻
