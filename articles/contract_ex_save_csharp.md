## はじめに

「バグがどこにあるかわからない...」
「データが保存されているはずなのに、DBを見たら空っぽだった...」

私が開発をしていると、そんな「なぞの挙動」に遭遇しました。
なぞの挙動ってデバックしんどいんですよね。

調査の結果、原因は良かれと思って書いた **「不適切な早期リターン」** が潜んでいたためでした。


今回は、C#を例に「契約プログラミング」という考え方を取り入れることで、開発者がどう幸せになれるかをお伝えします。

## よくある「なぞの挙動」が生まれる瞬間

例えば、リストを受け取って保存処理を行う、次のようなメソッドがあったとします。

```csharp
public void SaveUsers(List<User> users)
{
    // リストが空なら何もせず戻る（早期リターン）
    if (users == null || users.Count == 0)
    {
        return; 
    }

    // 保存処理...
    _database.Save(users);
}
```

一見、エラーも起きないし「安全なコード」に見えますよね。しかし、これが **「なぞの挙動」の入り口** です。

### 呼び出し側の誤解

このメソッドを使う側を想像してみましょう。

```csharp
var users = GetNewUsers(); // もしここでバグがあり、空のリストが返ってきたら？
_service.SaveUsers(users); 

Console.WriteLine("ユーザーの保存が完了しました！");
```

呼び出し側は、`SaveUsers` を呼んだ後に「保存が完了した」と信じて処理を続けます。しかし、実際にはメソッド内部でこっそりリターンされているため、何も保存されていません。

後になって「あれ、ユーザーが一人も登録されていないぞ？」と気づいたとき、原因が `GetNewUsers` なのか、`SaveUsers` なのか、それともDBの不具合なのか...。調査に時間が溶けていきます。

## 解決策：契約プログラミング（事前条件）

ここで「契約プログラミング」の考え方を導入します。
メソッドを呼び出す側と、呼び出される側の間で **「約束（契約）」** を結ぶのです。

「`SaveUsers` を呼ぶなら、必ず1つ以上の要素が入ったリストを渡してください。さもなければ、このメソッドは仕事を放棄（例外を発生）します」

### 改善後のコード

```csharp
public void SaveUsers(List<User> users)
{
    // 事前条件のチェック
    if (users == null) throw new ArgumentNullException(nameof(users));
    
    if (users.Count == 0)
    {
        // 「空のリストを保存しようとするのは、プログラムのバグである」と断定し、例外を投げる
        throw new ArgumentException("保存するユーザーが1件もありません。", nameof(users));
    }

    // 保存処理...
    _database.Save(users);
}
```

## なぜ例外を投げると「幸せ」になれるのか？

「例外を投げるとアプリが止まってしまうのでは？」と不安になるかもしれません。しかし、開発中にアプリが止まってくれることこそが **最大のメリット** です。

1.  **バグの早期発見 (Fail Fast):** 実行した瞬間に「空のリストを渡している」というバグが判明します。
2.  **責任の所在が明確:** スタックトレースを見れば、どの呼び出し元が間違ったデータを渡したか一発でわかります。
3.  **「なぞの挙動」が消える:** 「動いているように見えて、実は保存されていない」という不気味な状態がなくなります。

## 呼び出し側の「防衛的プログラミング」

メソッド側が厳しくなれば、呼び出し側も自然と注意深くなります。

```csharp
var users = GetNewUsers();

// 呼ぶ前にチェックする（防御的）
if (users.Any())
{
    _service.SaveUsers(users);
}
else
{
    // 空の場合の適切な処理（ユーザーに通知するなど）
    Log.Warning("保存対象がありませんでした。");
}
```

このように、**「メソッドを呼ぶ前に条件を満たしているか確認する」** ことで、より堅牢なプログラムになります。

もし万が一、予期せぬ場所から空リストが渡ってきても、メソッド側が例外を投げてくれるので、バグを野放しにすることはありません。

## まとめ

*   **黙って早期リターンしない:** 異常な状態（本来起こるべきでない状態）を隠さない。
*   **契約を明示する:** メソッドが必要とする条件を例外やドキュメントで示す。
*   **Fail Fast:** おかしいときは、すぐに、大きな声で（例外で）知らせる。

これらを意識するだけで、デバッグ時間は劇的に減り、コードの信頼性は上がります。
「例外を投げる勇気」を持つことが、開発者がちょっと幸せになれるコツです。

まぁ、開発中はついつい「なぞ挙動」を生み出しちゃうもんなんですよね。
コードを書いている瞬間はすべてが正しい気になっちゃって、テスト段階で過去の自分を殴りたくなりますよね（笑）

私個人の意見としては、テストコードも契約プログラミングも将来保守する自分を幸せにするためのツールだと思っています。
将来得するための投資みたいなものです。

そんなことを考えずに過去の誰かが書いた巨大なぞ関数をデバックする時の気持ちはもう、、、！！
